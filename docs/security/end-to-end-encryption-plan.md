# Circle 端到端加密方案

状态：2026-10-16，已接入仅文字加密的本地开发版本：App 收发、后端密文存储、设备批准/撤销、授权管理员浏览器解密。真实本地 HTTP + PostgreSQL 联调 13 项通过。当前覆盖、启动步骤、测试及未完成的恢复/真机验收边界见 [本地联调说明](text-encryption-local.md)。历史原型记录保留在文末，不能作为当前完成状态。

## 2026-10-16 产品要求修订：管理员可查看聊天

用户明确要求保留管理员查看所有会话中仍在保留期内聊天内容的能力。管理员必须被明确纳入可解密方，不能继续承诺“只有聊天双方能读”或“平台在任何情况下都无法解密”。本修订优先于下文原始方案中不允许管理员解密的假设。

密钥保管方式已由用户选定：**授权管理员设备解锁查看，业务服务器不持有解密私钥**。该方式已接入开发版本，通过功能开关和设备登记启用。下面保留两种方式的边界，第二种不采用：

- 已选择：授权管理员设备解密：业务服务器仅投递密文；管理员解密设备是公开披露的收件方，需要设备批准、私钥解锁和撤销流程。历史可读性取决于该接收方自启用时接收并安全保存的加密历史，不能通过事后加入 MLS 自动读取此前历史。
- 不采用：服务器托管解密：管理员沿用后台登录和权限查看；服务器具备解密能力。这是平台可解密的聊天加密，不能声称具有防服务器被攻破读取内容的端到端保密性。

无论选择哪种方式，都保留 `IM_READ`、有效 ADMIN 会话、查看理由、审计记录以及不缓存正文；普通账号或被撤权管理员不能因持有会话 ID 获得访问。审计日志不记录消息正文、搜索词或私钥。已撤回、焚毁、清理或超出保留期的内容继续按既有规则隐藏/删除，不因本次要求另留秘密明文副本。授权设备不能远程抹除已经读取或导出的内容。

验收需增加：授权管理员能够查看适用范围的加密记录、无权限账号拒绝、管理员设备撤销后的新密钥拒绝、密钥轮换与历史访问、审计失败不释放正文、用户端清楚展示管理员可访问范围。不得以另一份不受认证保护的“管理副本”代替对同一已认证消息的读取；若选用独立归档协议，必须验证两路内容一致性及故障恢复。

## 目标和范围（原始方案，按上方修订执行）

私聊、群聊的消息与附件在发送设备加密，在授权接收设备解密。后端、数据库、对象存储、反向代理和备份只持有密文及必要投递元数据。全程保留 HTTPS/WSS。公网防护采用自建 Caddy 与应用安全控制，不以采购云服务为前提。

端到端加密不隐藏账号、成员关系、消息时间、密文大小和 IP，也不保护已被控制的终端。收件人可以截图、导出或保留已解密内容；撤回、阅后即焚、踢设备不能保证抹除对方已保存的副本。

## 协议选型先行验证

优先验证 MLS（RFC 9420）用于私聊和群聊：每台设备是独立成员，统一处理群成员变化与密钥 epoch。备选为 Signal 系列协议，私聊使用其密钥协商、Double Ratchet 和多设备会话机制，群聊另评估成熟实现的组协议。不要自行设计“共享一个 AES 密钥”的消息协议。

开发可继续使用候选库验证与接入功能；第三方审计列入上线前验收，不作为继续开发或本地联调的前置条件。第一阶段继续验证：iOS/Android 原生绑定、React Native/Expo development build、Web/WASM（如果 Web 继续支持）、持久化状态的原子更新、依赖许可证、维护情况、安全审计和官方测试向量。以两个离线设备和成员变更 PoC 作为选型门槛；任一平台不可用时不能静默退回明文。

参考：[MLS RFC 9420](https://www.rfc-editor.org/rfc/rfc9420.html)、[Signal Double Ratchet](https://signal.org/docs/specifications/doubleratchet/)、[Signal Sesame 多设备会话](https://signal.org/docs/specifications/sesame/)。

## 密钥和设备身份

- 每台设备本地生成独立身份密钥；私钥不发送到业务服务器。原生设备用系统 Keychain/Keystore 包装密钥，协议状态在加密本地存储中原子持久化。具体库和安全存储能力通过 PoC 确认。
- 后端维护设备公钥目录和协议所需的公开材料，只授权当前账号操作自己的设备记录。登录信任设备与加密设备是关联但不同的状态，登录成功不会自动解锁历史消息密钥。
- 新设备由既有可信设备验证并批准，把加密身份纳入设备集合。对端可核对安全码/二维码；身份变化必须可见，不静默接受替换。
- 仅首次信任公钥（TOFU）无法阻止首次连接时恶意目录替换。生产前需要确定设备签名链与可审计密钥目录/透明度机制；界面不能宣称已核验未经核验的身份。
- 撤销设备后撤销 HTTP/WS 会话、停止投递，并更新相关会话密钥状态。旧设备不能得到未来 epoch 的消息；之前取得的明文和密钥不能远程收回。

## 消息、媒体和服务端改造

新增版本化加密信封，绑定会话 ID、发送设备、协议 epoch、客户端幂等 ID 及密文；具体字段跟随所选协议，不另造密码学格式。协议状态推进和本地待发送队列必须原子提交，避免崩溃后复用消息密钥。

保留现有 clientMessageId 幂等、height/revision 同步和投递 ACK。相同 ID 的重试发送完全相同信封，不能重新加密后当同一请求覆盖。服务端继续检查成员资格、禁言、信封大小和资源额度，但不解析密文里的业务内容。接收端验证协议认证和防重放，再解密与渲染。

附件在客户端用密码库提供的认证加密机制加密再上传。随机对象 key、附件密钥、文件名、缩略图和媒体元数据放入加密消息；存储层只持有密文。分块文件的 nonce、序号和完整性绑定由成熟实现负责。转发需要客户端解密后为目标会话重新加密，停用依赖服务器读取原文的转发路径。

编辑是新的加密事件；撤回/删除继续使用授权后的墓碑与同步水位。转账、通话等服务端事实回执保留独立的服务端签名和授权语义，不能把解密成功等同于支付真实发生。

## 与现有功能的冲突

| 现有能力 | 加密后的安排 |
|---|---|
| 服务端聊天全文搜索 | 改为设备本地索引，服务器不保留明文索引 |
| 敏感词检测 | 不能对服务器不可见的内容照旧扫描；产品需决定客户端检测及用户主动举报流程 |
| 客服自动回复、充值内容识别 | 加密会话默认停用；如把机器人加入为解密成员，必须明确展示并由用户选择 |
| 离线推送预览 | 默认“收到新消息”；需客户端安全解密能力后才考虑预览，推送服务不持有密钥 |
| 临时匿名聊天 | 暂不自动继承加密身份；单独完成访客密钥和设备验证设计后再启用 |
| 新设备历史同步 | 由已验证旧设备加密传输，或用户恢复密钥解锁的加密备份；服务器不保管恢复明文 |
| 媒体导入与笔记卡片 | 在客户端完成需要明文的转换；公共笔记本身仍遵循自己的分享权限，不能宣称因此加密 |

## 历史和升级

会话持久化 encryptionMode 与最低协议版本。启用后服务器拒绝旧客户端明文写入，禁止协商失败后回退明文。先灰度新的私聊，再群聊；开始灰度前应完成群方案 PoC，避免私聊选型堵死群迁移。

历史明文默认保留原有属性，并在 UI 中区分启用时间。若用户选择迁移历史，由可信客户端读取、加密回传并验证，再按数据库、对象存储、索引和备份各自的保留周期清理原文；不能承诺点击启用即可删除所有历史备份。

恢复默认使用用户持有的高熵恢复密钥或已验证设备；忘记密钥且没有可用设备会丢失加密历史，需要在启用前明确告知。不得用登录密码直接派生唯一恢复密钥，也不能让密码重置绕过加密恢复。

## 分阶段实施和验收

1. 协议与库 PoC：双端互通、离线首条消息、乱序/重复、协议状态崩溃恢复、大群成员变动、原生与 Web 可行性；完成许可证与维护审查。
2. 设备身份与恢复：设备签名链、安全码、批准/撤销、备份/丢失恢复测试，验证服务器替换公钥时客户端的实际行为。
3. 私聊和媒体：发送、编辑、转发、重试、撤回、附件损坏/截断/替换、重复 nonce 防护；抓取数据库、日志、推送和网络终止点，验证无明文/密钥泄漏。
4. 群聊与多设备：并发成员增删、离线跨 epoch、新成员无旧历史、移除成员/设备不能解密未来消息、管理员变更和重放攻击。
5. 小范围灰度：旧客户端拒绝与升级提示、断网/回滚路径、负载测试和独立密码学安全审查。回滚允许暂停新会话启用，不允许已加密会话降级明文。

完成上述验收前，产品只能标为开发中，不能宣称现有聊天已端到端加密。

## 2026-10-16 本地推进结果

使用固定版本 `ts-mls@1.6.4` 完成真实 MLS 双向/离线/乱序收发、上下文认证和重放拒绝、32 台设备加入/批量移除、新设备无历史密钥、移除设备不能解密未来消息、密文附件，以及加密 SQLite 中状态与 inbox/outbox 原子提交和重启重试。六组 MLS 工作组 suite 1 测试向量通过，完整互操作测试尚未完成。

原型只信任外部预置的设备公钥，尚无正式设备批准/恢复 UI。管理设备签署邀请并串行提交成员变更；这不是最终多管理员并发方案。

实测限制：此版本 Noble provider 仍经 HPKE 使用 WebCrypto X25519；在仅有安全随机数、没有 `crypto.subtle` 的环境中，密钥生成失败。原生支持必须通过适配器或原生绑定继续验证，不能把 Node 测试当作 iOS/Android 验收。上游也明确声明未经过正式安全审计，该事项安排在上线前；当前开发可继续接入和验证，产品状态必须与实际加密覆盖范围一致。

开发阶段继续解决平台适配、设备密钥包装/原子存储，并按上方阶段推进密钥目录、批准/恢复、密文投递与 UI；独立审查在上线前完成。完整复现命令、实验限制和依赖来源见 `circle-im/tools/e2ee-poc/README.md`。

### 开发阶段补充：无 WebCrypto 适配器

已新增 `portable-provider.mjs`：保留 MLS 与 HPKE 上游的协议实现，通过 HPKE 公共 DHKEM 接口及 Noble HKDF/AES 完成 suite 1 适配。没有 WebCrypto 的模拟环境下，完整协议测试和工作组向量通过；与默认 WebCrypto 实现互发消息和更新 epoch 的对照测试通过。系统安全随机源仍是必需项，缺失时拒绝初始化。

这解决了原先“无 SubtleCrypto 无法生成/使用密钥”的开发阻碍；Metro / Hermes / 真机以及安全存储还需要接入验证。第三方密码学审计不是开发停止条件，但仍属于上线验收。

### 2026-10-16 App 共用协议和原生存储准备

协议核心已提取到 `circle-im/packages/e2ee`，App 和原型共用相同依赖与算法实现。移除协议核心中的 Node 专用接口，加入异步 journal 支持、已确认设备身份的加密持久化、绑定操作与目标身份的签名接口。原生适配器使用 Expo SecureStore 和带 CAS 事务的加密 SQLite；存储失败拒绝操作，不回退明文。iOS / Android 独立入口 Metro 打包和 TypeScript 检查通过；尚未完成真机、后端投递和 UI 联调。

本轮还测量了 1 KB 文本、3 个设备的桌面原型基线：发送含落盘中位数 0.87 ms，接收含落盘中位数 1.36 ms。只代表本机 Node 测量，不作为手机性能承诺。用户正在确认是否将首次接入范围收窄到文字；在确认前不宣称媒体已有端到端加密。
