# 账号访问备用方案：受信任设备用不了时怎么进账号

陌生设备登录必须经受信任设备批准（见 `src/auth/device-trust.service.ts`）。这道门挡住了只知道密码的人，
但也带来一个必须兜住的风险：**用户唯一的受信任设备用不了时（丢失、恢复出厂、换新手机、
安卓重装、签名不同的包），不能把人永久锁在外面。**

本文列出所有备用通道，按「越靠前越快、越靠后越慢 / 越需要人工」排列。原则：

- 不依赖短信 / 邮件等外部付费服务也能自助找回（产品决定：不发验证码）。
- 每一条通道都要让「只知道密码的人」拿不到账号，或者至少让本人有足够时间发现并阻止。
- 每一次走备用通道都要通知本人的受信任设备，并留安全日志（`docs/logging.md`）。

## 通道一览

| 层级 | 通道 | 速度 | 前提 | 状态 |
|---|---|---|---|---|
| L0 | 另一台受信任设备批准 + 6 位码 | 即时 | 手边还有一台受信任设备 | 已上线 |
| L1 | 登录安全码 | 即时 | 事先设置过登录安全码 | 已上线（需引导设置） |
| L2 | 备用恢复码（一次性） | 即时 | 事先保存过恢复码 | **待做（建议）** |
| L3 | 等待期找回（24 小时） | 24 小时 | 无，App 端都能用 | **本次实现** |
| L4 | 邮箱找回密码 | 几分钟 | 注册邮箱可收信、服务端配了 SMTP | 代码已有，**生产环境不可用** |
| L5 | 人工客服重置设备信任 | 人工 | 客服核验身份 | **待做（建议）** |

另外，「同一台手机重装」本身不该触发备用通道：

- iOS：设备 ID 存在钥匙串，卸载重装后保留（已实测，前后 ID 一致）。签名团队变了才会丢。
- 安卓：安全存储随卸载清空。**本次改为新装时用 ANDROID_ID 加盐摘要作为设备 ID**，同一台手机、
  同一签名的 App 重装后不变。已经装着的老安装保留原随机 ID（会话绑定了它），它们下一次重装时
  仍会被当成新设备一次，由 L1–L5 兜底。

## L0 受信任设备批准（已上线）

新设备输密码 → 服务端只给验证单号、不发 token → 受信任设备弹窗「是否是你本人」→ 点「是我」拿到
6 位码（60 秒）→ 新设备输入后登录并成为受信任设备。拒绝 / 改密 / 全部退出都会作废验证单。

## L1 登录安全码（已上线，需引导）

设置过登录安全码的账号，新设备验证页可以「改用登录安全码」。每张验证单最多错 5 次，账号 24 小时内
累计错 10 次后停用这条通道；不动应用锁的错误计数。

**缺口**：默认没人设置。建议：账号只有一台受信任设备时，在「账号与安全」和设备管理页提示设置登录
安全码，作为最轻量的备用通道。

## L2 备用恢复码（建议做）

业界常见做法（GitHub / Google 都有）：在受信任设备上生成 10 个一次性恢复码，只显示一次，用户自己
保存（截图 / 抄写 / 存密码管理器）。新设备验证页「使用备用恢复码」→ 输入任意一个未用过的码 → 立即
通过并成为受信任设备，该码作废。

设计要点：

- 生成 / 重新生成只能在已登录的受信任设备上进行，并要求重新输入密码；重新生成会作废旧的一整组。
- 只存哈希（argon2），比对走与验证码相同的计次与账号级额度。
- 剩余少于 3 个时提醒重新生成；使用后通知其他受信任设备。
- 不依赖任何外部服务，和「不发验证码」的产品原则一致，是 L3 之外最重要的补位。

## L3 等待期找回（本次实现）

受信任设备全都用不了时，新设备在验证页点「受信任设备都用不了？申请找回账号」：

1. 申请后进入 **24 小时**等待期（`LOGIN_RECOVERY_DELAY_MS`）。所有受信任设备立刻收到推送 + 实时弹窗，
   弹窗里写明「不拒绝的话，对方将在 X 之后登录你的账号，并让你的其他设备退出」。
2. 等待期内以下任何一件事都会**取消申请**：任一受信任设备点「不是我」；任一受信任设备登录或续签
   （本人设备在用，能直接批准）；修改 / 找回密码；全部退出；退出其他设备；在设备管理里移除设备。
3. 等待期过后 7 天内（`LOGIN_RECOVERY_COMPLETION_WINDOW_MS`），在**同一台**设备上用密码重新登录即完成：
   这台设备成为唯一的受信任设备，其他设备的会话、信任和进行中的验证单全部撤销（多半是丢了的那台）。
4. 同一账号同时进行中的找回申请最多 3 个（`LOGIN_RECOVERY_MAX_ACTIVE`），防止被人占满挡住本人。
5. 网页端不提供：网页每次刷新都换设备 ID，做不到「等待期后在同一台设备上完成」。

安全边界：只知道密码的人也能申请，等待期就是本人发现并拒绝的窗口；只要本人的手机还在正常使用，
申请会被自动取消。比起没有这道门之前「知道密码即可登录」，这是严格更安全的；但对长期不打开 App
的账号，24 小时仍可能不够——这也是 L2 恢复码、L1 安全码值得补的原因。

## L4 邮箱找回密码（代码已有，生产不可用）

`POST /auth/password/reset` 校验邮箱验证码后改密，并撤销全部会话、全部受信任设备、全部验证单；之后
第一台登录的设备按「首台设备」直接放行。

**缺口**：

- 生产环境没有配置 SMTP，`UnconfiguredMailer` 直接 503，而 `requestPasswordReset` 吞掉了这个错误、
  对用户返回成功——用户以为发了验证码，其实永远收不到。至少要：配置 SMTP（或明确下线这个入口），
  并在发信失败时记错误日志 / 告警。
- 注册时不校验邮箱，邮箱可能根本不是本人的。L4 只能作为辅助通道。

## L5 人工客服重置（建议做）

管理后台目前只能封禁 / 解封 / 删除用户，封禁再解封**不会**清掉受信任设备，解不开锁。建议加一个
「重置设备信任」操作：

- 撤销该用户全部会话、全部受信任设备、全部进行中的验证单（等价于 L4 的效果，但不改密码）。
- 必须走管理台审计（`AdminAuditLog`）记录操作人与理由；客服先按既定流程核验身份。
- 操作后用户下一次登录的设备按「首台设备」放行。

## 运维速查：用户说「被锁在外面了」

1. 先问清：是不是只有一台设备、是不是重装 / 换机了、有没有设置登录安全码。
2. 有安全码 → 引导在验证页「改用登录安全码」（L1）。
3. 没有 → 引导在验证页「申请找回账号」，24 小时后在同一台设备重新登录（L3）。
4. 等不了 / 网页端 → 走客服核验后「重置设备信任」（L5，待做；做之前只能在数据库里手工撤销该用户的
   `TrustedDevice` 与 `RefreshToken`，并作废 `LoginChallenge`，务必留记录）。
